# Design

## Context

动机和能力范围见 [proposal.md](proposal.md)。仓库初始没有业务代码、依赖清单或既有规格；本次已通过 CLI 初始化本地 OpenSpec 根目录。约束为 Node.js 与 TypeScript、单房间最多 99 人、最多轮数配置 2～999、每轮作答时限 1～600 秒、匿名浏览器访问、内存存储，服务重启不恢复状态。

行为契约分别见 `specs/room-lobby/spec.md`、`specs/round-gameplay/spec.md`、`specs/game-results/spec.md` 和 `specs/session-recovery/spec.md`。这是首次实现，不建立兼容层、持久化抽象或迁移路径。

## Goals / Non-Goals

**Goals:**
- 用同一个可部署服务提供页面、HTTP 和实时连接，完成创建房间到再次开局的完整流程。
- 将规则、网络通信和界面分开，使计分和状态转换可独立验证。
- 在同时提交、超时、退出和重连时保证状态一致、每轮只结算一次且答案不提前公开。
- 限制房间历史和失联身份的生命周期，保证单进程内存使用可控。

**Non-Goals:**
- 不实现多服务、多实例、跨进程锁、事件溯源、数据库、账户系统或旧协议兼容。
- 不用客户端时间判胜负，不通过词典、AI 或模糊相似度判词。
- 不预先实现通用游戏框架、存储接口或规则插件。

## Decisions

### 1. 一个包管理项目，按职责分目录

采用当前运行环境可用的 Node.js 24 LTS 作为基线，实施时锁定依赖版本并提交锁文件；TypeScript 开启严格模式。使用 pnpm 和一个 `package.json`，无需 monorepo 工具或多个内部包。

| 目录 | 职责 | 主要依赖 |
|---|---|---|
| `src/client` | 页面、用户交互、连接状态及只读服务端状态投影 | React、Vite、Tailwind CSS、daisyUI、socket.io-client |
| `src/server` | HTTP、会话、房间状态、游戏规则、计时与公开数据投影 | Fastify、Socket.IO、Node.js 标准库 |
| `src/shared` | 命令和响应结构、输入校验、错误码、词语比较规则 | Zod |

服务端内部以独立模块分隔会话、房间操作、轮次转换和对外投影，不创建只有一个实现的接口或类工厂。共享模块不能导出服务器完整状态、凭据或可被客户端当成权威的计分状态。

取舍：原生 WebSocket 需要自行处理连接、确认和房间广播；Socket.IO 已提供这些基础能力。Next.js 的服务端渲染不服务于本游戏的核心需求，因此选择 Vite 构建浏览器端，Fastify 提供生产静态资源和 API。

### 2. 服务端内存是唯一业务状态

直接使用进程内集合保存状态，不封装可替换存储层：

| 状态 | 核心内容 |
|---|---|
| 匿名会话 | 不可猜测凭据、固定 playerId、关联房间、最近活动、当前连接 |
| 房间 | 房间码、房主、配置、加入顺序、连接与准备状态、状态版本 |
| 当前对局 | 随机 gameId、配置快照、初始参赛名单、有效／弃权状态、积分、当前轮 |
| 当前轮 | 轮数、阶段、服务器截止时间、每人首次接受的提交及请求 ID |
| 历史 | 已揭晓轮次、展示 ID 快照、原词、同词键、分组与积分变化、历史同词键集合 |
| 最近结果 | 不可变终局摘要及最近结束局的历史 |

匿名凭据使用 Node.js `crypto` 生成并通过 HttpOnly、SameSite Cookie 保存，生产环境启用 Secure；展示 ID 和 Socket.IO socket.id 都不承担认证职责。凭据与房间信息不进入日志正文或公开快照。

房间码使用标准库生成的 6 位无歧义大写字母／数字，并在内存中检查冲突。加入链接为 `/rooms/:code`。同一会话只关联一个房间，重复恢复不会增加成员。

SQLite 虽能保留状态，但用户明确不要求服务重启恢复；Redis 和多实例则引入跨进程状态协调，本期均不采用。

### 3. 房间阶段与对局阶段分离

```text
Room:
WAITING --> COUNTDOWN --> PLAYING
   ^            |           |
   |            v           |
   +--------- WAITING <-----+

Game while PLAYING:
COLLECTING --> REVEALING --> COLLECTING
     |             |
     +--> FINISHED <+
```

全员在线且准备后启动 3 秒倒数，倒数完成才创建 gameId、配置快照和初始参赛名单。倒数取消后原计时器失效，不创建半成品对局。准备阶段的房间人数是容量上限，默认 8 人、最多 20 轮、每轮时限 60 秒；这些是本提案的产品默认值，范围由规格固定。

开局条件使用同一处判断，在准备操作、准备阶段主动离开和失联成员过期移除后重检。倒数中成员离开仍只取消倒数，不在同一次操作中重新启动。

首次随机出词就是第 1 轮，计入配置的 2～999 轮上限。2 轮是最多轮数配置的最小值；首轮全员同词仍立即成功，人数不足仍立即失败，不为凑足实际游玩轮数而推迟终局。

参赛资格与连接状态独立：有效玩家断线仍保留本轮已接受答案；主动退出立即弃权；到作答截止时仍未答才因超时弃权。放弃本局可保留房间成员身份以查看结果；离开房间同时移除成员关系，但历史保留其展示身份与积分快照。

每轮配置的 1～600 秒是作答时间上限；当前轮全部有效玩家已答时立即结算，无须等待计时结束。普通揭晓持续 5 秒后开始下一轮，完整历史可回看。终局立即固化结果，将房间回到 WAITING 并清空准备标记；客户端单独显示结果页面，个人确认不改变共同结果，也不要求房主主持返回。

房主离开或断线立即转交给最早加入的在线成员；无人在线时暂空缺，第一位重连者接任。准备阶段的断线身份保留 120 秒，期间不能保持准备；期满移出。正常终局后仍断线的成员进入相同保留流程。

### 4. 统一词语键，区分历史与当前轮

词语规则模块使用 `trim()` 后的原文展示，以 `toLowerCase()` 结果生成比较键，完全不依赖浏览器语言或数据库排序规则。原文长度按 Unicode 码点计数，范围为 1～20；拒绝换行和控制字符。不进行简繁、全半角、标点、重音或同义词转换。

服务端提交校验顺序为：验证会话与当前活动连接、识别已接受请求重发、核对 gameId／轮次／阶段、处理已经到期的状态、验证参赛资格与未作答状态、校验词语及历史键，最后写入答案。正常操作必须重新读取到期处理后的阶段，不能继续使用旧状态。

历史键只来自已经结束并公开的轮次，包含当轮后来弃权但有合法提交者的已揭晓词；不包含未接受的尝试。当前轮提交不提前加入历史集合，因此多人可以独立提交相同新词。历史词拒绝只发给提交本人，不修改已答状态、不加分、不延时；客户端保留输入，提示“发送失败：该词已在之前轮次出现”，允许改词重试。

每次揭晓后将该轮全部已接受词的键加入历史集合；新一局使用新集合。成员展示 ID 使用相同的修剪和小写比较方式检测重名，但不加入词语历史集合。

### 5. 同步状态转换与可靠截止检查

房间的校验、状态修改和结算在同一个同步调用内完成，不在检查与修改之间 `await`。会话解析和输入解析完成后，所有游戏命令与计时器进入同一组状态转换函数；无需额外队列库或分布式锁。

服务进程使用单调时钟测量轮次和倒数持续时间，使用墙上时间记录统计日期并对客户端投影 `serverNow` 和 `deadlineAt`。每次相关命令处理都先比较权威截止时间；计时器只是触发检查的手段，事件循环延迟不能让迟到答案被接受。恰好到期即拒绝。

计时器闭包绑定房间、gameId、轮次和预期阶段；触发时再次核对，过期回调直接失效。阶段转换清理旧计时器，揭晓和终局设置防止再次结算的阶段标记。

结算顺序固定为：到期淘汰未答者 → 检查有效人数至少 2 → 等待或确认剩余全员已答 → 按键分组 → 全员同词加 100 并成功，否则各个多人组分别加 1 → 判断轮数上限 → 继续揭晓。退出造成不足 2 人立即终局，未完成轮不加分；揭晓后退出不回滚已经结算的积分。

### 6. 命令确认加状态快照恢复

Socket.IO 负责传输、自动重连和房间广播；业务恢复始终通过最新状态快照完成，不依赖恢复成功或逐条重放消息。自动重连不是会话身份来源。

| 入口 | 用途 |
|---|---|
| `POST /api/session` | 获取或恢复匿名 Cookie 会话，不把凭据放进响应正文 |
| `GET /api/rooms/:code` | 同源检查邀请是否仍有效，仅返回存在状态，不暴露成员或对局信息 |
| `GET /api/rooms/:code/games/:gameId/rounds?after=...` | 校验成员权限后，按游标返回最多 20 个已揭晓轮次 |
| `GET /health` | 部署健康检查，不返回房间或会话数据 |
| `room:create` / `room:join` / `room:leave` | 房间成员操作 |
| `room:configure` / `player:rename` / `player:ready` | 准备阶段操作，ready 使用明确布尔值而非切换指令 |
| `game:submit` / `game:forfeit` | 绑定 gameId 和轮次的对局操作 |
| `state:sync` | 当前公开状态与仅面向本人的私有状态同步 |

每条命令都有结构化确认 `{ ok, code, message, ... }`。提交携带 requestId、gameId 和轮次；每位玩家每轮只保存首次成功提交的请求及确认。相同请求重发从已有记录返回结果，即使已推进轮次也不再次修改；新的旧轮请求返回过期错误。客户端使用有限次重试，重连后以快照判断是否已答，不盲目重交输入框内容。

快照携带 roomVersion 和 gameId；客户端忽略旧版本。公开快照只包含当前阶段、成员、积分、提交标记、计时和最近结算摘要，当前未揭晓词只在本人确认或私有状态中出现。未揭晓历史接口同样不能泄露词语。公共投影使用显式字段构造，不序列化完整房间对象再让前端隐藏字段。

同会话的新连接接管活动连接并通知旧连接停用；旧连接的后续命令和延迟断线回调须校验连接身份，不得误淘汰新连接。HTTP 和实时入口校验同源来源与会话，所有客户端负载在服务端经过 Zod 校验。

### 7. 历史与内存清理保持有界

实时更新不重复发送完整历史；最多 999×99 份提交以已揭晓轮次存放，历史页面按需读取。终局只主动推送统计摘要和最后一轮，历史继续分页可查。房间只保留当前局与最近结束局；新结果替换旧结果后释放更早记录。

历史界面每次查询取消上一请求并清除旧页面，取消的请求不能更新结果、错误或加载状态；组件卸载时同样取消请求，避免切换对局或轮次后被旧响应覆盖。

空房立即销毁，销毁时取消全部计时器。准备阶段使用 120 秒失联清理；对局阶段由轮次截止淘汰未答者，不另加会延长参赛资格的重连宽限。退出房间的匿名会话可复用，但无房间关联且闲置 24 小时后释放。清理使用普通服务内计时，不引入后台任务系统。

服务重启时所有集合丢失。旧 Cookie 不对应有效会话，旧房间链接返回失效提示；浏览器应提供回首页、创建或加入入口，不尝试用本地存储的词语、分数或名单重建对局。

### 8. 页面由共同状态驱动

- 首页：输入展示 ID，创建房间或输入房间码；邀请链接也经过相同身份检查。
- 准备页：房间码和邀请链接、成员连接状态、房主配置、明确的准备／取消准备操作及规则说明。
- 对局页：当前轮与上限、剩余时间、上一轮分组、提交状态、自己的输入或已提交内容、历史入口和弃权操作。
- 揭晓：列出词语、对应玩家、分组及本轮加分，显示下一轮倒数。
- 结果页：成功庆祝或失败原因、共同词与完整统计、按轮历史、个人确认返回准备。

界面以服务端状态更新分数和阶段，不乐观计算胜负。断线时保留本地输入草稿、禁止假提交，显示正在恢复及倒计时继续的提示。表单带标签、可用键盘操作、错误与焦点反馈明确；不用颜色作为唯一状态提示，庆祝动画遵循减少动态效果偏好。用 daisyUI 组件和语义色构建移动与桌面布局，不新增第二套组件库。

页头主题按钮通过原生 Popover 和 daisyUI theme-controller 提供全部内置主题，主题名称直接读取 daisyUI 的导出列表。默认不固定 `data-theme`，由 daisyUI CSS 根据系统偏好使用 light／dark；手动选择保存在本地，选择“跟随系统”清除手动选择。主题仅属于客户端，不进入房间状态或实时协议。

## Risks / Trade-offs

- [服务重启会清空房间与对局] → 这是已确认的行为；部署文档和失效页面明确说明，不伪造恢复结果。
- [剩余玩家可在有人弃权后达成成功] → 这是已确认的淘汰规则推导；终局显示初始人数、完成人数和弃权人数，避免把剩余全员描述为最初全员。
- [历史词禁用会使长局逐步收窄可选词] → 输入失败明确说明原因并保留改词机会，不改变原截止时间，也不使用模糊匹配扩大禁词范围。
- [同一个人可使用不同浏览器伪装多人] → 匿名房间不承诺实名或强反作弊；不把展示 ID 唯一性当成人类身份验证。
- [单进程有资源上限] → 单房间以 99 人和 999 轮限制，历史按需查询并及时清理；不宣称全平台无限并发，部署规模通过实际观测确定。
- [消息丢失或重发造成界面暂时落后] → 请求确认、每轮首次提交记录、状态版本和重连快照共同收敛；不假设传输层提供业务上的恰好一次交付。

## Deployment

首次部署使用一个支持长连接的 Node.js 服务，HTTPS 由部署平台或现有反向代理终止，并转发 Socket.IO 连接。Fastify 提供 Vite 构建产物及 API；开发环境用 Vite 代理保持同源 Cookie 语义，不需要第三个业务服务。

实施时提供安装、开发、类型检查、聚焦验证、生产构建和启动命令，以及单实例和重启清空的运行说明。无旧数据迁移；回滚为重新部署上一份构建，重启同样会终止现有房间。

## Validation

使用 Node.js 自带测试能力配合 TypeScript 运行工具验证容易在界面上漏检的关键分支：词语键与跨轮禁词、多个同词组、最后一轮成功、到期边界、弃权前后结算和重复提交。网络层只增加少量真实客户端集成检查，验证答案不泄露、断线恢复、会话接管和旧请求不会进入下一轮。

完成类型检查与生产构建后，用至少两个浏览器会话验证创建、准备、同词成功、失败和再开一局；用协议客户端检查 99 人容量、最多轮数 2～999 及作答时限 1～600 秒的配置边界，并验证首轮计数和全员提前提交立即结算。只验证本次能力，不搭建全站测试平台或负载基准体系。
