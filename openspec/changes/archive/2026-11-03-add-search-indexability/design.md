# Design

## Context

参见 [proposal.md](./proposal.md) 的 Why。以下是影响实现路径的现状事实。

**交付链路。** 客户端是 Vite 单页应用，`root` 为 `src/client`，输出到 `dist/client`。两种托管方式须对齐状态码与索引指令：

- Nginx 直接托管 `dist/client`（[deploy/nginx.conf](../../../deploy/nginx.conf)），`/api/`、`/socket.io/`、`/health` 转发到 Node 进程。
- Node 本地预览（[app.ts](../../../src/server/app.ts) 的 `production` 分支）注册 `@fastify/static` 托管同一目录，并单独注册 `app.get("/rooms/:code")` 回退到 `index.html`。

发现文件和首页依赖资源也由同一份 `dist/client` 提供，不能因排除独立索引而被禁止抓取。

**回退规则。** Nginx 当前为 `try_files $uri $uri/ /index.html`，未知路径返回 200 首页。Node 侧的 `@fastify/static` 使用 `wildcard: false`，只做逐文件匹配，未知路径本来就返回 404 —— 两条链路当前行为不一致。

**文案与语言。** 文案在 [messages.ts](../../../src/client/i18n/messages.ts) 的 `zh` / `en` 字典中，键集合由 [messages.test.ts](../../../src/client/i18n/messages.test.ts) 校验。[locale.tsx](../../../src/client/i18n/locale.tsx) 优先读取手选语言，否则检测浏览器语言，并更新页面标题与 `lang`；因此英文浏览器会把静态中文首页替换为英文。

**渲染方式。** [main.tsx](../../../src/client/main.tsx) 用 `createRoot(...).render()` 挂载，不是 `hydrateRoot`。`#root` 初始为空，任何预置内容都会被首次渲染直接替换。

**配置。** 已有 `PUBLIC_ORIGIN` 用于公开访问来源。Vite 配置执行时不会自动把仓库根目录 `.env` 注入 `process.env`，构建插件需要使用 Vite 的环境加载能力显式读取。

## Goals / Non-Goals

**Goals:**

- 只将规范首页 `/` 作为可索引页面，其他 URL 的排除信号在两条托管链路一致。
- 让默认首页在不执行脚本和执行脚本时均提供真实中文内容，且文案只有一个来源。
- 直接使用现有环境加载、静态托管与语言包能力；图片生成不进入部署构建。
- 区分本地技术检查、线上抓取和实际搜索效果，提供可执行的交付清单。

**Non-Goals:**

- 不增加任何其他可索引页面，包括英文页、玩法子页、FAQ 子页或房间页；不做语言路由与 `hreflang`。
- 不引入服务端渲染框架或 `hydrateRoot` 改造；首页仍然是纯客户端应用。
- 不为 `/rooms/:code` 生成邀请预览卡片；这类链接一律不可索引。
- 不承诺排名、流量或收录时间，不新增自动推送服务、定时监控或分析 SDK。

## Decisions

### 构建期生成同源元数据与真实正文

`index.html` 是构建产物，正文注入放在 Vite 插件里做，产物落在 `dist/client/index.html`。

**为什么不是服务端拼装：** 生产环境的首要托管者是 Nginx，HTML 根本不经过 Node 进程。若在 Fastify 里拼装，就必须把 Nginx 的 `try_files` 改成反代到 Node，等于为了 SEO 把静态托管改成动态托管，还让每次首页请求都穿过 Node。构建期注入对两种托管方式同时生效，且零运行时成本。

**为什么不是 `hydrateRoot`：** 预置的正文与 React 渲染树之间的结构必须严格对齐才能 hydrate，而首页结构由 `inviteCode`、`online`、`busy`、`language` 等状态分支决定，首帧环境无法复现服务端假设。降级为纯文本注入后，React 挂载时直接替换，不需要任何对齐契约。

**注入内容：** 使用语义标题和段落写入 `#root`，包含主标题、多人联机文字联想游戏介绍、邀请朋友的方式、规则和一个简短玩法示例。客户端首页同步展示同一批内容，使用既有 daisyUI 组件与 Tailwind 类；不只给爬虫添加文案，也不新增独立内容路由。

**文案来源：** 插件从 `messages.ts` 读取 `messages.zh.document` 与 `messages.zh.home`。补充描述、游戏说明、玩法示例和图片替代文字，并补齐英文对应键。注入时正确转义文本与属性；结构化数据使用安全的 JSON 序列化。静态元数据与正文共同表达品牌和游戏用途，不要求机械重复关键词。

> 备选：把文案写进 `index.html` 注释，构建时替换。被否，因为它制造了第二个来源。

### 只复用 `PUBLIC_ORIGIN`，生产构建不提供来源回退

`vite.config.ts` 使用 `loadEnv` 按当前 mode 从仓库根目录读取 `.env` 配置，遵循环境变量优先级；只取现有 `PUBLIC_ORIGIN`。生产构建校验其为真实 HTTPS 公网来源，不含凭据、非根路径、查询参数或片段；本地地址和示例占位域名不能通过。使用标准 `URL` 解析并取规范化的 `origin`，统一派生 `${origin}/` 与各资源地址。

缺失或非法来源使 `pnpm build` 失败并给出配置错误。`pnpm dev` 不生成发布用索引地址，不要求公开来源。生产预览使用按真实来源构建的同一份产物，不把本地预览地址写入 canonical；README 说明本地访问地址与产物声明来源的区别。这样不会出现构建成功却把本地地址发布到搜索引擎的情况。

`robots.txt` 与 `sitemap.xml` 由插件在 `writeBundle` 阶段写入 `dist/client`，与首页 canonical、`og:url`、分享图及结构化数据共用此来源。sitemap 固定生成首页一个 `<url>`，不扫描文件或路由自动扩充。

**为什么 `robots.txt` 不能是提交好的静态文件：** 它可以，但 sitemap 的绝对地址不行，而两者必须一致。统一生成比一半静态一半生成更容易解释。

### 首页、文件别名、房间与未知路径分别处理

| 请求                                          | 响应与索引策略                                                                   |
| --------------------------------------------- | -------------------------------------------------------------------------------- |
| `/`，含其查询参数变体                         | 200，无 `noindex`，canonical 始终指向不带参数的规范首页                          |
| 外部请求 `/index.html`                        | 301 到 `/`，携带 `noindex`，不直接提供第二份首页                                 |
| `/rooms/[A-Z2-9]{6}`                          | 提供邀请页面并携带 `noindex`；格式合法不等于房间仍存在，失效邀请继续显示既有状态 |
| `/api/`、`/socket.io/`、`/health`             | 保持业务响应；普通 HTTP 响应携带 `noindex`，WebSocket 升级不作为网页索引入口     |
| 实际存在的静态资源与发现文件                  | 正常提供并携带 `noindex`，允许抓取和作为首页或预览依赖                           |
| 未知页面、无效房间码、`/en/` 等未定义语言路由 | 404 与 `noindex`，不回退首页                                                     |

Nginx 的首页和房间 location 用 `try_files /index.html =404` 在当前请求处理上下文提供文件，避免把 `/index.html` 的外部重定向规则应用到内部文件交付。其他静态请求只使用 `try_files $uri =404`；保留既有接口反代。Node 同步增加文件别名重定向，并在房间 HTML 路由校验相同的六位大写格式，不能只在 API 校验。

**房间格式依据：** 服务端 API 已使用 `^[A-Z2-9]{6}$`。两条 HTML 托管链路采用相同约束，避免 Node 对任意房间段都返回 200 而 Nginx 返回 404。

**注意大小写：** Nginx 房间正则显式使用 `(?-i:...)` 关闭忽略大小写，不依赖平台默认值，与 `[A-Z2-9]` 一致；`App.tsx` 读取路径后对房间码做了 `toUpperCase()`，因此手输小写的链接会得到 404。这是有意的取舍 —— 房间码本身不接受小写，重定向会制造重复 URL。此行为需在部署说明里写明。

房间格式错误直接返回 404；这里不增加大小写重定向。永久重定向只用于归并实际存在的首页文件别名，并不把重定向本身视为独立索引内容。

### 抓取许可和索引许可分开，只有首页不设置 `noindex`

`robots.txt` 使用 `User-agent: *`、`Allow: /` 和绝对 `Sitemap` 地址，不对房间、接口或静态资源追加 `Disallow`。禁止抓取会让支持 `noindex` 的搜索引擎无法读取排除信号，因此不作为排除索引的兜底。

响应头根据外部请求 URL 决定，首页及其参数变体不设置 `noindex`，其他 URL 设置 `X-Robots-Tag: noindex`。房间和首页使用同一 HTML 文件，因此不得在共享 HTML 中加入静态 `noindex`。

Nginx 使用原始 `$request_uri` 计算响应头策略，不能用会被内部文件处理改写的 `$uri`；头部使用 `always` 覆盖错误响应，并核对 location 的头部继承，防止首页误禁或房间漏禁。Node 在 Socket.IO 完成监听器注册后，为底层 HTTP server 前置统一的 `request` 监听器，按原始请求路径设置同一规则；该入口同时覆盖 Fastify 的静态文件、接口与未找到响应，以及绕过 Fastify 的 Socket.IO polling、客户端脚本和拒绝响应，无需分散维护两套头部逻辑。验收同时检查 GET 与 HEAD、直接访问与重定向后的首页。

这些是系统交付给搜索引擎的指令，不是对所有外部爬虫行为的保证。百度与 Bing 的实际抓取、收录和非首页误收录情况分别观察；发现非首页结果时按对应平台实际可用的删除或诊断工具处理，不通过全面禁止抓取掩盖问题。

### 位图资源一次性生成并提交，不进构建

`og-image.png`、`apple-touch-icon.png` 与 `icon-*.png` 由脚本从手写的 `icon.svg` 光栅化产出，产物提交到 `src/client/public/`。

**为什么不进构建：** 位图只在品牌或文案改动时需要重做，让每次 `pnpm build` 都跑一遍 Rust 系光栅化除拖慢构建外没有收益，还让部署机多一个原生依赖。

**为什么仍然引入 devDependency：** 因为图标必须有确定性来源，手工在外部工具里导出会让「矢量源文件是唯一设计来源」这条不可验证。脚本 + 源文件让重生成是可复现的命令。

**分享图内容：** 尺寸固定为 1200×630，使用同一套品牌和游戏介绍文案，显式指定中文字体族；缺少字体时生成失败，不静默退化成不可读图像。图片与引用完整性属于发布检查，卡片是否最终展示由外部平台决定。

### 压缩在 Nginx 层启用

`gzip` 覆盖 `text/html`、`text/plain`、`application/javascript`、`text/css`、`application/xml`、`image/svg+xml`；`gzip_types` 不含 `image/png`，因为 PNG 已内建压缩。

**为什么不在 Fastify 侧做：** 生产环境 HTML 与静态资源由 Nginx 提供，Node 只服务 `/api/`、`/health` 与 `/socket.io/`。响应体最大的部分不经过 Node，在 Node 侧加压缩等于把开销放在了错误的位置。

**本地预览的偏差：** Node 预览不启用压缩。这是可接受的 —— 生产路径有压缩，本地预览用于验证功能而非测量性能，因此不引入 `@fastify/compress` 只为对齐一个非功能性差异。

### 默认首页固定中文，保留手动语言选择

静态壳的标题、描述、`lang`、结构化数据都用中文；初始化语言顺序为：有效的手选持久化偏好、首页默认中文、非首页按原有浏览器语言检测。这是本次对 `client-localization` 的显式修改，记录在 [语言 delta](./specs/client-localization/spec.md)，不把行为变化藏在索引能力中。

全新浏览器直接访问 `/` 时，无论浏览器首选语言是中文还是英文，脚本执行后的首页均保持中文。手动切换仍立即生效并记忆，`lang` 和标题继续跟随所选语言；不按爬虫 User-Agent、IP 或特殊请求头分流内容。英文界面没有独立索引 URL，首页 canonical 与分享元数据继续声明同一中文默认入口。

### 上线清单分开记录技术条件与搜索效果

README 保留简短发布入口，详细清单放在 `docs/search-indexability.md`：在真实来源上检查大陆网络和移动端访问、无脚本与有脚本内容、路由响应矩阵、依赖资源和压缩；不能用 `pnpm dev` 代替对构建产物的检查。

优先验证百度搜索资源平台与 Bing Webmaster Tools，仅提交规范首页；有 sitemap 权限时提交仅一条首页的站点地图，没有权限时使用平台实际提供的首页链接提交方式。平台验证文件或 DNS 验证按当前入口操作，文件验证通过普通静态资源路径提供，不新增可索引页面或长期保存推送凭据。

记录品牌查询及“多人联机文字游戏”“默契联想游戏”等与实际内容相关的中文查询作为初始观察项，不声称已有搜索量证据。技术发布后记录抓取诊断与索引状态，并在上线后一周、一个月人工复查首页收录、非首页误收录及展现和点击；无数据就记录无数据，不建立定时服务。实际收录与流量仍待搜索引擎处理，不能由资源存在、平台提交成功或 `site:` 查询单独证明。

**参考依据：** [Vite 配置中的环境加载](https://vite.dev/config/#using-environment-variables-in-config)、[Nginx 文件检查与内部重定向](https://nginx.org/en/docs/http/ngx_http_core_module.html#try_files)、[Bing 排除 URL](https://www.bing.com/webmasters/help/?topicid=264e560a)、[百度普通收录说明](https://ziyuan.baidu.com/linksubmit/index)。

## Risks / Trade-offs

- [预置正文与 React 首帧样式不一致会产生可见跳变] → 预置容器复用 `HomeScreen` 的同一组 Tailwind 类；构建后目视核对首屏，窄屏 320px 与桌面各看一次。
- [分享图依赖系统中文字体，缺字体时文字可能错乱] → 生成脚本显式指定字体族并允许失败时报错；产物提交到仓库，构建不重复生成，因此只在重新生成时才会暴露该问题。
- [收窄回退后，用户手输小写房间码会得到 404] → 房间码在界面上始终大写显示、邀请链接始终大写；在 README 部署说明中写明该行为。
- [Nginx 配置未同步更新的部署会继续软 404] → proposal 已标为 BREAKING；README 中把配置更新列为部署必做项，并给出可验证的 `curl` 检查。
- [搜索引擎未采纳指令或未收录首页] → 分引擎记录抓取和索引状态，按平台诊断；不承诺排名、流量或处理时限。
- [无手选偏好的英文用户首次打开首页看到中文] → 页头仍提供即时语言切换并记忆，邀请入口继续使用浏览器语言；不新增英文索引路由。
- [构建来源不正确导致整份索引元数据漂移] → 生产构建必须通过真实来源校验；发布前比对配置、canonical 与 sitemap，发现错误直接修正并重建。
- [构建期读取语言包把客户端模块引入 Node 构建脚本] → 插件只导入纯数据模块 `messages.ts`，它不触碰 `document`/`window`；`check-boundaries.mjs` 只禁止客户端导入服务端，反向不受影响，但需在实现时确认该模块保持无 DOM 依赖。

## Migration Plan

1. 配置真实 `PUBLIC_ORIGIN`，生成并提交图片，完成文案、默认语言与构建插件修改，产出新的静态文件。
2. 对同一份构建产物验证 Node 生产预览和 Nginx 配置；执行 `nginx -t`，核对首页、别名、有效与无效房间、未知页面、接口和静态资源的 GET/HEAD 响应。
3. 以一次发布同步更新静态产物、Node 与 Nginx，旧的全路径首页回退规则直接移除，不保留兼容分支；发布失败时恢复上一份完整发布产物与配置。
4. 在实际公网来源完成抓取与资源检查后，仅提交首页。技术发布验收与后续搜索效果观察分开记录，归档不以获得排名或流量为条件。
