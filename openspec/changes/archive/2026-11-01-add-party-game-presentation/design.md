# Design

## Context

动机与范围见 `proposal.md`；可验收的行为见 `specs/game-presentation/spec.md`。

已观察到的实现约束：

- 客户端使用 React 19、Tailwind CSS 4、daisyUI 5；`style.css` 目前只导入框架并启用全部主题，没有专用动效依赖。
- `App.tsx` 同时承载首页、邀请入房与准备页面；`game-screen.tsx` 包含作答、答案和结果。`RoundAnswers` 也由 `history.tsx` 使用，不能在其挂载时无条件庆祝。
- 对局视图按 `gameId-round` 设置 React key，新一轮会重新挂载。把已播记录放在该组件内部会导致上一轮参考再次播放。
- `use-room.ts` 通过 `state:sync` 接收快照，连接建立后主动同步，过滤较旧版本但允许同版本；其返回值没有区分实时更新和首份恢复快照的来源标记。
- `RoundView` 已提供 `completed`、答案原文、弃权、实际加分与服务端同词组；`Result` 已提供共同词、结束原因、人数及最终轮次。无需推导胜负或新增服务端事件。
- 当前没有浏览器组件测试框架；已有测试使用 `tsx --test` 和 Node 测试能力。现有规格要求完整结果可查、全部主题可选、服务端权威计时和隐私边界。

## Goals / Non-Goals

**Goals:**

- 建立从 320px 单列起步的页面与交互，减少找到线索、作答和返回准备所需的浏览成本。
- 通过短暂、有限、与真实结果对应的反馈形成轻派对气质；静态页面自身就能完整表达所有状态。
- 将页面排版、状态传输、动效触发判断和粒子资源管理分开，后续页面复用不会意外重放。

**Non-Goals:**

- 不修改共享协议、同词键、计分、阶段时长、邀请行为、主题持久化或结果个人确认规则。
- 不加入音效、震动、自定义动效开关、通用事件总线、动画编排框架或 UI 组件库。
- 不同时保留旧布局及新布局，不增加兼容分支或状态迁移。

## Decisions

### 1. 采用已选定的明快轻派对方向

探索时比较了两种方案：明快轻派对保留稳定的思考空间，在揭晓和成功时集中反馈；强舞台派对使用更多全屏转场和粒子，现场感强但更占窄屏注意力。用户已选择前者。

延续现有文字品牌和全部主题，以圆润卡片、清楚字号、语义色和少量局部装饰统一气质。主操作使用 daisyUI 按钮，次级信息使用卡片、状态、徽章、统计或原生可展开区域；实施前读取对应组件技能。不固定一套浅色背景，不另建主题系统。

### 2. 先交付完整静态窄屏流程，再叠加动效

页面先在没有动画的情况下完整工作，然后逐层增加确认、揭晓、分组、成功反馈。避免把布局可用性依赖于动画编排。

窄屏各页默认组织：

| 页面 | 首要区域 | 次级区域 |
| --- | --- | --- |
| 首页与邀请 | 紧凑品牌说明、展示 ID 和当前适用的入房操作 | 规则简述、主题及连接信息；邀请保持现有专用表单 |
| 准备房间 | 房间码与邀请、准备进度、准备按钮和倒数 | 成员明细、房主设置、离开房间 |
| 作答 | 轮次与时间、上轮线索、输入或锁定答案、提交人数 | 玩家积分及状态、放弃与离开、历史 |
| 揭晓 | 本轮词语、同词组、加分、下一轮剩余时间 | 玩家详情与历史 |
| 结果 | 原因、共同词、人数和轮数耗时摘要、返回准备 | 完整并列排名、时间、弃权明细、最终答案和历史 |

大量线索先展示紧凑摘要并提供“查看全部 N 条”，初始可见条数由实施者在 320px 下确定；所有答案原文与玩家归属必须可查，展开不能改变作答状态。大量成员以提交或准备摘要带明确明细入口，主按钮排在长列表之前。结果页的返回按钮位于摘要之后、长统计之前，保持个人确认语义。

基础容器与网格使用可收缩子项、可换行文字和适配的内边距；不通过整页隐藏横向溢出来掩盖布局问题。窄屏页头允许换行，主题弹层限制在可视区域内。宽屏才增加辅助列，DOM 与焦点顺序保持一致。

移动输入沿用原生表单，输入字号至少 16px，主要控件至少 44×44px。默认采用文档流操作区，配合安全区域留白，不添加会被软键盘覆盖的固定底栏。仅真实阶段转换可以设置合适焦点；成员快照、分数更新与动效不重新聚焦、不重设草稿、不主动滚动。错误沿用可见消息和字段关联。

备选方案是先设计桌面大舞台再缩放；它不能解决窄屏参考、输入和长列表的顺序问题，因此不采用。

### 3. 组件按页面和资源职责拆分

按实际改动从 `App.tsx` 提取首页／邀请表单与准备房间组件，使 App 保留连接、命令和页面选择。将 `RoundAnswers` 抽成独立答案展示组件供对局、结果和历史复用：它渲染服务端答案、分组和静态强调，不在挂载时启动音效、粒子或计时器。

在不随轮次 key 重建的 App 层放置专用的表现状态 hook／小型转换函数，负责把已接受状态变化转为一次短暂表现请求；新建独立彩带组件拥有 canvas 和清理逻辑。实时容器向答案组件显式传入临时反馈标记；参考与历史始终走静态展示。

不新增可配置的动画注册表、通用事件总线或重复的 UI 游戏状态机。组件和文件的具体名称交给实施者，但上述生命周期边界固定。

### 4. 通过连接来源和阶段变化识别实时庆祝

仅比较 `phase` 或只在 `useEffect` 挂载时播放都不足以区分重连。`use-room.ts` 在每次连接建立后，将第一份实际接受的快照标记为恢复基线，并把连接代次与快照一起作为仅客户端的元数据暴露；不扩展 `Snapshot` 的网络类型，也不在传输层执行动画。表现层每次换连接代次先建立基线，随后才识别本连接内实时变化。

表现层保留当前房间／对局、最近观察到的公开轮次，以及本局成功是否已处理的有界记录。初始化、断线或接管、切换房间、页面隐藏及恢复可见都重建观察基线，并把已存在结果视为已处理。记录不放在每轮重建的 `GameScreen` 中，不向本地存储写入动效历史。

| 新状态 | 触发条件 | 表现 |
| --- | --- | --- |
| 成员准备、本人答案锁定 | 本页在线可见时观察到服务端确认的未完成到完成转换 | 对应状态短暂强调；失败不触发 |
| 开局倒数 | 当前真实倒数状态 | 用现有截止时间和服务器偏移显示当前整数秒；恢复时只显示当前秒，不回放前面的数字 |
| `REVEALING` 的新轮次 | 同局首次公开该完整轮次，且非恢复基线 | 答案入场，按 `groups` 对至少两人组提供反馈 |
| 新失败结果 | 最终轮完成且该轮尚未处理 | 若有有效同词组，播放局部 +1；不播成功彩带 |
| 新成功结果 | 正在向本人展示本页实时观察到的新成功 | 共同词与实际 +100、一次彩带；抑制同轮部分同词 +1 |
| 历史、参考、重复／恢复状态 | 不满足实时条件 | 只显示静态结果 |

有效组直接使用 `playerIds`，奖励使用 `points`，不按词语原文自行再分组。未完成轮次不匹配；揭晓后再退出不修改服务端已结算分组。直接到达终局也从 `Result.finalRound` 判断，覆盖首轮成功与最后一轮部分同词。

表现请求在生成时即记录为已处理；重复快照、React 重渲染或开发模式的 effect 检查不会重新创建请求。已处理请求的 effect 重启只管理同一请求的资源，不发放新的播放资格。若在减少动态效果、不可见或断线时被跳过，就保持已处理，不在稍后补播。恢复到在线可见后真正的新阶段仍可触发。

准备反馈只用于本人已返回准备视图的状态，不替换本人结果页仍在播放的反馈。其他成员独立确认并准备，不中断本人当前成功庆祝。邀请状态检查仅在在线时挂载，断线即取消，重连重新检查；首页表单继续保留草稿。

### 5. CSS 负责局部反馈，单一粒子库负责彩带

使用 CSS 的透明度与小幅 transform 完成确认、倒数、轻弹、浮现和过渡；不逐帧改变布局尺寸，不为每位玩家启动 JavaScript 计时器。CSS 时长和 easing 集中在 `style.css` 的少量表现变量中，不做运行时配置系统。

建议初始节奏如下，实施者可在既定上限内微调：

| 反馈 | 初始节奏与上限 |
| --- | --- |
| 准备／提交确认 | 约 150～250ms，一次性强调 |
| 开局倒数 | 每次显示当前整数秒时短暂弹入，不延长 3 秒倒数 |
| 揭晓／局部同词 | 约 400～800ms；全部入场不超过 1 秒；组间并行，不按人数排长队 |
| 成功 | 共同词约 400ms 入场；两侧有限彩带总计 2～3 秒内结束 |
| 失败／下一轮 | 约 150～250ms 柔和过渡，内容与操作随真实阶段立即可用 |

彩带使用 [canvas-confetti](https://github.com/catdad/canvas-confetti)，复用其有限粒子、`disableForReducedMotion` 和 `reset` 能力。它是唯一新增的运行时动画依赖；类型如需补充只使用对应类型包。采用单个组件自有 canvas，装饰层 `pointer-events: none`、不进入辅助技术内容，不在每张答案卡片创建 canvas。候选 Motion／GSAP 会引入当前效果不需要的编排能力；自行实现粒子物理则增加资源管理代码，均不采用。

以 640px 为粒子预算分界：窄屏一次成功最多 60 个粒子，宽屏最多 120 个，两侧喷发共享总预算。组反馈以全组静态高亮和同步轻弹为核心，额外星点共享单次预算，窄屏最多 12 个、宽屏最多 24 个；不会为每个成员或组创建独立粒子循环，所有组仍有明确对应关系。颜色从当前主题的可用强调色派生，文字和分数继续使用语义色。

canvas 清理同时调用实例 `reset`、取消未发生的喷发并移除资源；不等待 Promise 完成才允许返回。首轮成功也必须有可用彩带资源，不依赖上一轮提前加载。

### 6. 无障碍和取消是表现生命周期的一部分

CSS 使用 `prefers-reduced-motion` 禁止位移与缩放；粒子层启用库的减少动态效果选项，并监听偏好在运行中的变化以立即取消已启动效果。关闭偏好不生成旧请求。准备、匹配与得分仍有完整文字和静态高亮。

隐藏页面、断线、接管、切换房间、动画所属阶段失效及卸载都取消相关表现；恢复可见或首份恢复快照只建基线。装饰不持续循环、不捕获点击、不主动抢焦点。保留结果标题的合理焦点和错误反馈；阶段摘要使用适当状态播报，倒计时不用每秒更新的 live region。

### 7. 验证覆盖真实风险，不搭建新框架

实施时为表现转换的纯逻辑增加最小 Node／tsx 测试，集中覆盖首份同步、连接代次、重复轮次、参考重挂载、终局直接到达和隐藏／偏好取消后的不补播。这些分支仅靠视觉浏览很容易漏检。测试不模拟 CSS 细节，不引入 DOM 或端到端测试框架。

浏览器验收使用独立会话完成静态流程和动效流程：320／360／390px 与至少一种手机横屏、桌面，正常和 20 码点长文本、小房间和 99 人边界、多组同词、首轮成功、轮数用尽、人数不足、历史、刷新、重连、接管、后台、动态偏好、浅／深色主题。软键盘与安全区域在可用的真实移动浏览器验证；桌面尺寸模拟不能冒充真实键盘验证，环境不具备时明确记录未验证项。

验证遵循项目约定：本次规划只运行 OpenSpec 校验与文档差异检查；实施阶段运行对应表现逻辑测试和浏览器检查，达到至少四个核心交互文件改动时按约定运行相关检查，不默认运行无关服务端全套。README 同步外观、动效与窄屏验收说明。

## Risks / Trade-offs

- [99 人线索过长，主操作被推离] → 紧凑参考摘要、可展开完整归属、主按钮优先于长明细；不隐藏已揭晓数据。
- [恢复状态误当新结果或下一轮 key 造成重播] → 快照关联连接代次、稳定表现层、公开轮次与成功记录；按直接终局和多次同步验证。
- [CSS 延迟或粒子抢占窄屏交互] → 总时长与总粒子预算、并行分组、transform／opacity、单 canvas 和立即取消；无需额外动画设置。
- [多主题强调失去对比] → 语义色、可见文本和局部强调；至少验证浅／深色与一套不同强调色的内置主题。
- [软键盘或自动聚焦打断阅读] → 文档流操作区、稳定输入节点、仅阶段级焦点策略，真实移动浏览器验证。
- [设备性能差异使固定帧率承诺不可靠] → 不承诺统一帧率，验收有限资源、操作不阻塞和及时清理；在较低性能手机观察交互。

## Migration Plan

不涉及数据或协议迁移。按静态页面、普通反馈、实时分组、成功彩带的顺序实现，每一步保持完整可玩。完成后按现有流程安装依赖并构建同一版本前端；需要回退时回退完整前端及依赖锁文件，不保留双布局或兼容运行路径。
